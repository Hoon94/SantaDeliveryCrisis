## 1. 담당자별 업무

| 담당 | 팀원 이름 | 작업 번호 | 담당 업무 | 주요 작업 위치 |
| --- | --- | --- | --- | --- |
| **A · 세션·저장 로직** | __________ | **1의 로더 + 2** | 시드 JSON 검증·최초 주입, 카테고리 하나의 출제(약한 문제/오래 안 푼 문제)·후보 수 계산, 카테고리 추천 배지 계산(`TaskRecommending`), 채점, 세션 시작·저장·이어 풀기·완료, 보상·트리 데이터 관리 | 출제·세션·트리 서비스, 시드 로더 |
| **B · 퀴즈·애니메이션** | __________ | **3 + 5** | 퀴즈 진행(S4), 정오답 피드백(S5), 결과(S6), 오답 노트(S7), 코드 실행 애니메이션, 효과음·햅틱 재생 | `Features/Quiz/`, `Features/Trace/`, 피드백 서비스 |
| **C · 작업실·출제 화면** | __________ | **4 + 8 중심** | 작업실(S1), 출제 필터 팝업(S2), 장식 선택(S2-B), 진행 중 세션 시트·알림(S2-A1/A2/E1), 트리 표시·완성 연출, 공통 이미지 자산 취합 | `Features/Task/`, `Features/Select/`, 트리 공통 뷰·이미지 자산 |
| **D · 문제 관리·학습 기록** | __________ | **6 + 7** | 문제 목록·편집·삭제(S10/S11), 미디어 첨부, 주·월 통계(S9), 설정 화면(S12), 완성 트리 수 표시 | `Features/Manage/`, `Features/Records/`, `Features/Settings/`, 통계 계산 서비스 |

**분리 원칙:** A는 계산·저장, B·C·D는 서비스 호출과 화면 표시를 담당한다. B·C·D는 보상 계산이나 세션 완료 처리를 화면에 따로 구현하지 않는다. D의 문제 CRUD 저장과 통계 계산은 D의 범위이며, A가 모든 데이터 처리를 대신 맡는다는 뜻은 아니다.

작업 0(기반)은 완료되어 develop에 있다. 작업 9(마감)는 D가 취합하고 전원이 자기 화면을 점검한다 `[가정]`.

## 2. 공동 작업 분배

| 공동 업무 | A | B | C | D | 완료 기준 |
| --- | --- | --- | --- | --- | --- |
| **문제 작성** | AI 활용 | Swift 문법 | HIG | SwiftUI 실전 | 카테고리별 쉬움·보통·어려움 각각 최소 5개, 총 최소 15개씩 |
| **문제 검수** | D 작성분 검수 | A 작성분 검수 | B 작성분 검수 | C 작성분 검수 | 보기 4개·정답·해설·난이도·태그·출처 링크 확인 |
| **시드 통합** | 형식·ID 검증과 로더 연결 | 담당 문제 전달 | 담당 문제 전달 | 담당 문제 전달 | 최소 60문제, 중복 주입 없음. 애니메이션 ID는 B와 대조 |
| **이미지 자산** | 필요 자산 공유 | 장면에 필요한 캐릭터·배경 요청 | 파일명·규격·등록 취합 | 관리·기록에서 필요한 자산 요청 | 임시 자산 교체 후 사용 화면에서 확인 |
| **효과음** | — | 파일 규격·재생 연결 취합 | 제작 협조 | 제작 협조 | 정답·오답·완성 소리가 설정에 따라 동작 |
| **문서·시연 자료** | 실행 방법·로직 설명 | 풀이·애니메이션 시연 | 작업실·출제·완성 시연 | 작성·조회·통계 시연 | 각자 작성 후 최종 취합 담당 1명 지정 |

문제 작성자는 자기 카테고리의 모든 난이도를 맡는다. 시연을 위해 문제를 더 늘릴지는 팀에서 정한다. 애니메이션 문제의 유형·실행 단계·`animationID`는 B와 먼저 맞춘다.

시드와 자산은 서로 다른 파일로 준비하고 A 또는 C가 최종 등록을 취합한다. 여러 사람이 같은 `questions.json`이나 공통 자산 파일을 동시에 직접 수정하는 일을 줄인다.

## 3. 기능 연결 책임

| 연결 지점 | 제공 담당 | 사용하는 담당 | 합의할 내용 |
| --- | --- | --- | --- |
| 문제 선택·세션 시작 | A | C | 카테고리 하나의 선택 출제, 후보 개수 부족 시 가능한 만큼 출제, 0개 처리 |
| 카테고리 추천 배지 | A | C | `TaskRecommending`이 카테고리 하나 또는 nil을 돌려주고, C는 nil이면 배지를 표시하지 않음 |
| 제출·채점·복원·결과 | A | B | 제출 인덱스, 현재 위치, 결과 값, 중복 호출·저장 실패 처리 |
| 코드 애니메이션 | B | B의 퀴즈 화면·A의 시드 로더 | 장면 ID·단계 데이터·재생 완료 신호·장면 누락 처리 |
| 트리 진행·완성 기록 | A | C·D | 현재 트리와 완료 여부, 완성 기록 조회·갱신 |
| 트리 공통 표현 | C | B·D | 진행도와 완료 상태를 받아 표시하는 공통 뷰. 결과 화면의 완성 연출에서 재사용 |
| 완성 연출 | C | B | C가 연출 뷰를 제공하고 B가 세션 결과 화면에서 호출. 연출에서 보상 재지급 금지 |
| 문제 수정·삭제와 미디어 | D | A·B·C | 공통 미디어 서비스 사용, 진행 중 스냅샷 보호, 삭제된 문제의 오답 제외·후보 갱신 |
| 설정 | 공통 키·저장소는 기반 계약 | A·B·D | D는 편집 화면, A는 세션 시작 시 기준값 보존, B는 사운드·햅틱 설정 적용 |

## 4. 파일 충돌을 줄이는 규칙

| 수정 대상 | 주 담당·변경 방법 |
| --- | --- |
| `Models/`, 공통 프로토콜·결과 타입 | A가 변경을 취합. `TaskRecommending`은 아직 코드에 없으므로 A가 가장 먼저 `Protocols.swift`와 mock에 추가해 develop에 병합. 필요한 담당자가 먼저 사용 사례를 공유하고 기존 계약과 함께 수정 |
| `AppServices.swift`, `MainTabView.swift`, `ModelContainerFactory.swift`, Xcode 프로젝트 설정 | A가 통합 변경 취합. 각 담당자는 자기 화면·서비스를 제공 |
| `SettingsStore`와 공통 미디어 서비스 | 기반 공통 코드로 취급. 변경은 A와 사용 담당자가 함께 검토하고 한 PR에서 반영 |
| 기능 화면·기능 전용 서비스 | 각 담당자가 자기 영역에서 수정. 같은 `Services/` 폴더여도 서로 다른 파일로 분리 |
| 공통 트리 뷰·색상·이미지 자산 | C가 취합. 자산 이름과 뷰 입력값을 먼저 공유 |
| 시드 JSON | 각자 카테고리별 작성본을 전달하고 A가 최종 형식에 맞춰 통합 |
| 공통 명세 | 계약 변경 시 관련 문서·mock·사용 코드도 함께 갱신. 자기 기능만 맞도록 공통 타입을 따로 만들지 않음 |

A의 취합은 다른 사람의 모든 변경을 대신 작성한다는 뜻이 아니다. 공유 파일을 바꾸는 PR을 한 번에 하나씩 검토·반영하는 조정 역할이다.

브랜치는 기반 코드가 병합된 최신 `develop`에서 기능별로 만든다. 예시는 아래와 같으며 한 사람이 모든 업무를 한 브랜치에 오래 쌓아둘 필요는 없다.

| 담당 | 브랜치 예시 |
| --- | --- |
| A | `feature/session-engine`, `feature/seed-loader` |
| B | `feature/quiz-flow`, `feature/code-trace` |

## 5. 병렬 개발과 통합 순서

| 단계 | 함께 확인할 담당 | 확인할 결과 |
| --- | --- | --- |
| **준비** | 전원 | 작업 0의 남은 공통 수정과 모델·프로토콜·mock 정합성 확인. 이름과 경로가 같은 기반 코드로 시작 |
| **첫 연결** | A + B | 일반 문제 하나 → 제출 → 저장 → 앱 재실행·복원 → 결과 → 보상 |
| **출제·관리 연결** | A + C / A + D | 출제 설정·장식 선택으로 실제 세션 시작. 사용자가 만든 문제도 조건에 맞게 출제 |
| **표현·기록 연결** | B + C / A + D | 결과의 트리 완성 연출, 완성 직후 완성 트리 수 갱신, 통계·설정 연결 |
| **애니메이션 연결** | B + A·C | 시드 장면 ID와 재생기·자산 연결, 재생 후 피드백·다음 문제 진행 |
| **최종 확인** | 전원 | [통합 시나리오](integration-contracts.md)의 항목, iPhone/iPad, 라이트/다크, 접근성, 문서·시연 자료 |

전원이 기능 개발을 시작할 수 있지만, 첫 통합은 각 기능이 모두 끝나기 전에 진행한다. mock으로 화면만 만든 상태와 실제 서비스 연결 완료는 구분한다. B의 퀴즈·애니메이션 작업량이 커지면 C가 자산 제작을 지원하고, B는 일반 풀이 흐름부터 연결한 뒤 애니메이션을 붙인다.
